# 编辑器修订模型路由与故事状态输出预算设计

日期：2026-07-30

## 背景

项目 3 的第一章修订任务 757 已成功完成修订稿生成、候选验收和正文持久化，但后处理连续暴露了两个独立问题：

1. `post_quality` 没有透传修订任务输入中的 `model_id = 36`，因而回退到项目审查阶段的默认 Google 模型，供应商返回 `403 PERMISSION_DENIED`。
2. 修复模型路由后，`post_quality` 使用 `claude-sonnet-4-6 / cliproxyapi` 成功完成；随后精确故事状态同步仍固定使用 4500 个输出 token。模型返回被截断，准备结果同时带有 `story_state_invalid_payload` 和 `story_state_transport_incomplete`，安全门以 `STORY_STATE_PREPARE_BLOCKED` 拒绝应用。

任务 757 的正文已经安全持久化，候选哈希为 `c95ad16c4fb21c4545a5ee393b9fd5f9a660dd1faf95d00ee85d426c268b93d5`。本设计不得重新生成或重新提交该正文。

## 目标

- 修订任务选择的模型必须贯穿正文生成、修订后质检和当前章故事状态同步。
- 故事状态模型输出预算必须成为项目级可配置项，以适应不同模型的输出能力。
- 截断或无效的故事状态准备回执不得在“继续后处理”时永久复用。
- 每次任务尝试仍只执行一次应用层故事状态生成，不恢复自动二次调用。
- 所有修复保持严格单章作用域，不修改后续章节正文。
- 已保存的修订正文、质检结果和有效恢复回执不得重复执行或回滚。

## 非目标

- 不修改修订正文的结构化输出协议。
- 不降低故事状态安全门，不接受截断 JSON，不启用确定性状态降级。
- 不根据模型名称维护一套易过期的硬编码能力表。
- 不自动修改模型管理器中的模型级输出配置。
- 不批量同步全部章节的故事状态。

## 方案比较

### 方案 A：可配置单次预算与坏回执定向刷新（采用）

精确故事状态同步保持一次应用层模型调用；项目设置提供输出预算。只有准备结果明确因无效 payload 或传输不完整而失败时，后续“继续后处理”才丢弃该坏回执并读取最新配置重新准备。

优点：调用次数可控，保持安全门和恢复语义，并允许用户在切换模型后人工调高预算。

### 方案 B：恢复应用层自动重试

第一次截断后自动再请求一次更大输出。

不采用：会重新引入多次模型调用和不可预测的长运行，而且第二次仍可能被截断。

### 方案 C：截断后跳过或确定性降级

不采用：任务表面完成，但后续续写缺少可靠状态，违背故事状态完整性要求。

## 配置模型

在项目的 `reference_config.editor_revision` 下增加：

```json
{
  "editor_revision": {
    "timeout_seconds": 600,
    "story_state_max_tokens": 9000
  }
}
```

规则：

- 默认值：`9000`
- 最小值：`1000`
- 最大值：`262144`
- API 只接受有限数字，服务端截断为整数并限制到有效范围；界面只允许提交整数。
- `262144` 与现有模型管理器的输出长度硬上限一致，不把正文生成代码中的 32000 档位误当成模型能力上限。
- 设置超过 `64000` 时，界面显示供应商兼容性、费用和耗时风险提示，但允许保存。
- 供应商或模型不支持所填预算时，保留明确错误，不静默截断、钳制到未知值或切换模型。

现有 `GET/PUT /api/novel/projects/:id/editor-revision-config` 同时承载超时与故事状态预算。PUT 支持旧客户端仅提交 `timeout_seconds`，也支持只提交新字段；未提交字段保留当前归一化值，项目其他 `reference_config` 内容必须完整保留。

## 运行时快照

修订检查点的运行配置扩展为：

```ts
runtime_config?: {
  llm_timeout_ms: number
  story_state_max_tokens?: number
}
```

新任务在首次解析运行配置时把两个有效值一起写入检查点。已有任务可能只有 `llm_timeout_ms`，解析器必须补齐缺失的新字段，同时保留旧超时快照。

正常崩溃恢复继续复用已保存的预算，避免项目设置在一次活动任务中途无条件漂移。

唯一例外是故事状态阶段因以下准备错误失败后，由用户显式执行“继续后处理”：

- `story_state_invalid_payload`
- `story_state_transport_incomplete`

此时重试转换必须：

1. 保留已完成的正文生成、候选验收、正文持久化和修订后质检阶段。
2. 删除坏的 `story_state.prepared`，不删除有效或已应用的状态回执。
3. 清除检查点中的 `story_state_max_tokens` 快照，使本次显式继续读取项目的最新配置。
4. 把 `sync_current_story_state` 重置为待执行。
5. 不触发正文模型、正文提交或已完成质检。

其他失败类型不得清除预算快照或有效准备结果。

## 模型路由

`post_quality` 调用必须显式传递 `input.model_id`。故事状态准备和应用继续传递同一个 `input.model_id`。

故事状态准备新增 `maxTokens` 输入，并将检查点快照中的 `story_state_max_tokens` 传给底层 `prepareStoryStateUpdate`。应用阶段使用已准备结果，不再发起第二次模型调用。

模型选择优先级不变：任务显式模型优先于项目阶段默认模型。本修复不允许 `post_quality` 回退到另一个供应商。

## 项目设置界面

现有“项目设置 → 质检与修订”增加“故事状态输出上限”数字输入框：

- 单位：token
- 默认：9000
- 范围：1000 至 262144
- 步长：512
- 超过 64000 显示非阻塞风险提示
- 加载失败时继续禁止保存，避免默认值覆盖服务端已有配置

说明文字应明确：该值只控制修订后“当前章故事状态同步”的单次模型输出预算，不控制正文长度，也不会扩大到全部章节。

## 错误处理与安全边界

- 截断或无法解析的状态 JSON 继续失败关闭，不能写入项目 Story State。
- 坏准备结果在当前尝试中先持久化，确保错误可诊断；只有用户显式继续时才定向清除。
- 章节候选哈希和单章回执绑定保持不变，恢复前必须重新验证章节 61 的正文仍匹配候选哈希。
- 后续章节只能产生既有的确定性连续性告警，不得修改其正文、版本、标题或章节状态。
- 用户已有的 `workspace/assets.json`、`workspace/zhuque-inputs/` 和 `workspace/zhuque-reports/` 不纳入代码提交。

## 测试设计

### 服务端纯配置测试

- 缺失、非法、小于下限和大于上限值的归一化。
- 默认返回 `{ timeout_seconds: 600, story_state_max_tokens: 9000 }`。
- 最大值 262144 可保存，超过最大值按服务端规则归一化。

### 配置路由测试

- GET 返回两个归一化字段。
- PUT 可分别或同时更新两个字段。
- 更新时保留 `editor_revision` 其他字段和全部兄弟配置。
- 非数字、非有限值返回 400。

### 工作进程回归测试

- `post_quality` 接收到任务 `model_id`。
- 故事状态准备接收到检查点中的 `story_state_max_tokens`。
- 检查点已有旧超时但没有新字段时只补齐新字段。
- 正常恢复复用运行时快照，不受项目设置中途变化影响。
- 截断准备结果失败后，显式继续清除坏准备结果和 token 快照，读取最新项目配置。
- 显式继续不调用正文模型、不重新提交正文、不新增章节版本，也不重复已完成质检。
- 有效准备结果仍在崩溃恢复时复用。

### 前端测试

- 正确加载默认值和服务端值。
- 校验整数与 1000 至 262144 范围。
- 保存 payload 同时支持超时和故事状态预算。
- 超过 64000 显示风险提示但保存按钮仍可用。

### 真实验收

1. 使用 `claude-sonnet-4-6 / cliproxyapi` 和项目 3。
2. 将故事状态输出预算设为 9000 或更高。
3. 对原任务 757 执行“继续后处理”，不得创建新的修订任务。
4. 确认 `post_quality` 保持已完成，故事状态重新准备时使用模型 ID 36 和新预算。
5. 确认任务 757 完成，或若模型仍超过预算，则返回明确截断错误并允许调高配置后再次继续。
6. 确认章节 61 的修订版本数量不增加、正文哈希不变。
7. 确认其余 29 章的正文、更新时间和版本指纹不变。
