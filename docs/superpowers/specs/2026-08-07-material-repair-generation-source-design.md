# 材料补齐 GenerationSource 设计

日期：2026-08-07

## 背景

MangaForge 已将章节正文、复检、修订和 Story State 等实际生成阶段纳入项目唯一的 `GenerationSource`。项目启用模型 API 时由所选模型执行；项目启用 MCP 时由绑定的 MCP Server、Key、Adapter 和 Agent 执行，并且每次实际生成调用使用独立远端 Agent Session。

真实页面验收暴露了材料补齐链路的缺口：

- 工作区的“补齐材料”和“生成正文”入口仍无条件要求 `selectedModelId`，导致只启用 MCP 的项目显示“请先选择模型”；
- `/auto-repair-context` 仅在请求包含 `model_id` 时调用模型，否则使用确定性材料兜底；
- 章节生产服务在材料修复完成后才创建章节 `GenerationSource` 任务，因此 MCP 不会参与材料生成；
- 设定工坊和章节设定调用的页面补齐入口也直接依赖模型 API。

这不是单纯的前端校验问题，而是“材料补齐”没有被建模为 GenerationSource 生成调用。若只移除页面校验，MCP 项目仍会把确定性模板误当作模型补齐结果，也无法证明项目唯一来源得到遵守。

## 已确认决策

- 采用独立的 `material_repair` GenerationSource 任务。
- 一次“补齐材料”操作只创建一个独立远端 Agent Session。
- 世界观、角色卡、角色状态、章节蓝图、设定实体和章节设定调用等本次缺失材料在同一次结构化调用中生成。
- 材料补齐 Session 结束后不得用于正文；随后的正文生产创建新的独立 Session。
- 项目当前激活的 GenerationSource 是本次补齐的唯一生成来源。
- MCP 失败不回退模型 API，也不使用生成式确定性模板冒充远端结果。
- MCP 设计必须 provider-neutral，不在通用编排层加入 Buda 身份、工具名或页面特例。
- MCP 扩展不得改变现有模型 API 的选择、请求、降级、响应或其他章节生产功能。
- 本期仍只覆盖章节生产链及其写作前置材料，不扩展到章节生产链外的创作工具。

## 方案比较

### A. 独立材料补齐任务

为材料补齐增加通用执行端口和结构化输出合同。MCP 使用一个独立 Agent Session 返回本次所有缺失材料；模型来源包装现有 API 实现。手动补齐和正文启动时的自动补齐共用同一服务。

该方案明确保持唯一来源、Session 边界和原子保存，也能隔离模型 API 兼容路径，因此采用此方案。

### B. 在正文任务内部增加材料阶段

改动较少，但材料补齐会和正文任务共享生命周期。修复保存后，任务最初固定的上下文版本可能失效；恢复、来源切换和失败回滚也会与正文产物耦合。

### C. 分别把现有材料接口改为 MCP 感知

可以复用多个页面接口，但一次补齐会产生多个远端 Session，角色、世界观和设定可能基于不同上下文独立生成，也无法提供整次操作的原子结果。

## 架构边界

### 材料补齐编排器

新增单一职责的材料补齐编排器，例如：

```ts
interface MaterialRepairExecutor {
  repair(input: MaterialRepairInput): Promise<MaterialRepairResult>
}
```

编排器负责：

- 读取项目、章节和当前材料；
- 计算本次缺失项及请求合同；
- 解析项目当前激活的 GenerationSource；
- 固定项目、章节、来源指纹和上下文版本；
- 调用对应的模型或 MCP 执行器；
- 校验并规范化结果；
- 对 MCP 结果执行原子持久化；
- 返回更新后的材料状态和来源回执。

编排器不解析 MCP 工具，不读取 Buda 配置，也不自行选择备用来源。

### GenerationSource 阶段合同

在章节生成阶段类型中增加：

```text
stage: material_repair
response_contract: material_repair_json
```

该阶段仍通过现有 `ChapterGenerationSource` / `GenerationInvocation` 边界执行。模型实现和 MCP 实现消费相同的业务输入与结果合同，但各自保留自己的调用方式。

MCP 通用适配继续使用现有单阶段调用能力：同步本次权威上下文、创建一个远端 Agent Session、启动一次任务、轮询终态并提取结构化结果。Buda 只作为现有 MCP Adapter 的一种实现；通用材料编排不得依赖 Buda 的工具名称或 Agent 限额。

“一个独立 Session”指一个远端 Agent Session。底层 MCP Transport 可以按既有稳定策略恢复或轮换，但不得因此创建第二个结果不确定的 Agent Session。

### 两个执行器

`McpMaterialRepairExecutor`：

- 不要求 `selectedModelId`；
- 使用项目绑定且已启用的 MCP 来源；
- 将本次全部缺失项合并为一次自包含请求；
- 一次操作只创建一个远端 Agent Session；
- 不完整或不合法的响应视为整次失败。

`ModelMaterialRepairExecutor`：

- 继续要求并使用现有 `selectedModelId`；
- 包装现有 `/auto-repair-context`、设定孵化和章节设定调用逻辑；
- 保留现有提示词、模型参数、降级规则、响应字段和持久化语义；
- 不因引入 MCP 改写正文、复检、修订或其他模型 API 路径。

统一的是能力入口、来源选择和可比较的结果摘要，不强制把模型 API 改造成 MCP 的单 Session 调用方式。

## 输入与输出合同

### 输入

材料补齐输入必须自包含，至少包括：

- 项目身份、题材、简介、风格和写作圣经；
- 当前章节目标、摘要、冲突、章尾钩子、已有蓝图和场景卡；
- 世界观、角色卡、角色当前状态和信息边界；
- 设定实体、项目设定调用和本章设定调用；
- 最近章节摘要、Story State 和连续性材料；
- preflight 的缺失 key、证据、修复要求和严格就绪合同；
- 明确的 `material_repair_json` 输出 schema；
- 项目、章节、来源和上下文身份哈希。

不得把远端 Agent 历史记忆当成缺失输入。远端记忆只能辅助执行，本次请求携带的 MangaForge 权威上下文优先。

### MCP 结构化结果

结果按本次请求的缺失项返回可选分区，例如：

```json
{
  "chapter_patch": {},
  "worldbuilding": [],
  "characters": [],
  "character_updates": [],
  "settings": [],
  "chapter_setting_usage": [],
  "repair_summary": ""
}
```

具体字段沿用现有小说实体 schema。服务端只接受本次请求允许修复的分区，拒绝跨项目身份、正文、来源配置和其他越权字段。

“完整结果”不是要求无条件生成每一种实体，而是要求对所有请求的缺失项给出满足 schema 和最低数量/质量约束的结果。已有且通过检查的材料默认只读；空值不得覆盖已有内容。

确定性代码可以做：字段别名归一、类型转换、长度限制、去重、引用解析和安全默认值。它不得创造人物经历、世界规则、章节冲突、设定内容或其他小说语义来代替 GenerationSource。

## 执行流程

### 页面手动补齐

1. 页面读取服务端返回的章节 GenerationSource 权威状态。
2. 模型来源继续校验 `selectedModelId`；MCP 来源校验绑定和运行就绪，不检查模型 ID。
3. 页面提交项目、章节和可选缺失 key，不提交来源覆盖。
4. 服务端重新读取项目并确定唯一来源，不能信任前端推断。
5. 编排器构建完整材料输入，固定来源指纹和上下文版本。
6. MCP 创建一个 `material_repair` 远端 Agent Session；模型执行器进入现有 API 逻辑。
7. MCP 结果整体完成 schema、业务约束、来源和上下文校验。
8. 再次确认项目来源和上下文身份未变化。
9. MCP 结果在同一事务内写入全部实体及章节引用；失败则全部回滚。
10. 页面重新加载世界观、角色、设定、章节设定调用、Story State 和材料评分。

### 正文启动时自动补齐

1. 正文入口使用相同的来源感知校验，不因 MCP 项目没有模型 ID 而提前阻断。
2. preflight 不就绪且允许自动补齐时，先调用同一个材料补齐编排器。
3. 材料任务成功关闭后重新读取所有实体并重建章节上下文。
4. 严格 preflight 通过后才创建正文生产的本地任务和远端 Agent Session。
5. 材料补齐 Session 与正文、复检、修订 Session 均相互独立。

自动链路不得先创建正文任务再修改其上下文版本，也不得复用材料补齐的回执作为正文来源回执。

## 页面设计

- 把无条件的 `selectedModelId` 判断替换为来源感知的可执行状态。
- 模型来源继续显示原有“请先选择写作模型”。
- MCP 来源在绑定、测试或运行就绪失败时显示对应 MCP 错误，不误报模型缺失。
- “补齐材料”进度明确显示当前使用 MCP 或模型 API。
- 成功提示展示实际补齐项和新材料评分，不展示 Key、完整 Agent ID 或完整 Session ID。
- 补齐失败后保留当前页面材料，允许用户修复绑定或重试；不得在 UI 侧自动切换来源。
- “生成正文”入口使用同一来源感知规则，避免补齐修复完成后仍被旧模型校验阻断。

## 一致性、失败与恢复

### MCP 原子提交

MCP 返回内容先进入内存中的 staged mutation。所有创建、更新和引用替换在单一 SQLite 事务中提交。事务开始前再次验证：

- 项目和章节仍存在；
- 项目激活来源未改变；
- authority/source fingerprint 与任务开始时一致；
- 输入所依赖的上下文版本未被并发修改；
- 结果覆盖所有请求的必要缺失项；
- 所有实体引用能够解析且属于当前项目。

任一条件失败时不保存任何本次 MCP 内容。

### 失败分类

- 绑定或来源未就绪：返回现有 GenerationSource 类型化错误。
- MCP 输出合同不合法：返回材料响应校验错误，不进入模型或模板降级。
- 来源或上下文变化：返回任务失效错误，要求基于最新状态重试。
- 明确未派发的 MCP 错误：按既有稳定策略在总预算内安全恢复。
- 结果不确定的 mutation：沿用现有 quarantine 规则，禁止盲目重放。
- 客户端取消：沿用已确认的标准 HTTP 提交语义；页面重新读取服务端权威状态。

模型 API 路径继续使用现有错误映射和降级语义。MCP 的更严格原子性不得倒逼本期修改模型路径。

## 来源回执与可观测性

材料任务记录有界审计信息：

- 本地 task ID、project ID、chapter ID；
- `material_repair` 阶段和响应合同；
- 来源类型、authority/source fingerprint 和 context version；
- Adapter、Agent、Session 和 snapshot 的安全标识；
- 请求缺失 key、结果分区、输入/输出 hash、终态和错误码；
- 是否原子提交及提交后的材料评分。

不得记录原始 Key、自定义认证 Header、账号密码、完整提示词、完整远端错误体或页面可复制的完整远端身份。真实验收输出同样遵守该规则。

## API 兼容性保护

MCP 支持采用显式分支实现，不改变模型来源默认行为：

- `active === 'model'` 时继续走现有模型补齐实现；
- 模型项目仍必须选择模型，现有请求参数和响应字段保持兼容；
- 未配置 `chapter_generation_source` 的旧项目继续按现有模型来源规则解析；
- 现有正文、场景卡、复检、修订、Story State 和编辑器接口不因材料 MCP 扩展改变；
- 通用 MCP 默认稳定策略和非 Buda Adapter 行为保持不变；
- 不允许为了通过 MCP 测试而放宽模型 API 的校验或质量门。

测试必须先锁定现有模型行为，再增加 MCP 路径；任何模型快照或契约变化都视为回归，除非另行设计和确认。

## 测试设计

实现采用 RED-GREEN-REFACTOR。

### 来源路由和合同测试

1. 模型来源仍要求 `selectedModelId` 并调用原有模型补齐逻辑。
2. MCP 来源在没有模型 ID 时可以执行材料补齐。
3. 服务端忽略客户端来源覆盖，只使用项目当前激活来源。
4. MCP 失败不会调用模型 API 或生成式确定性兜底。
5. 旧项目和显式模型项目的现有响应合同保持不变。

### MCP Session 测试

6. 一次补齐多个材料分区只创建一个远端 Agent Session。
7. 成功的材料 Session 不被后续正文复用。
8. 材料、正文、复检和修订各自拥有独立阶段回执。
9. 通用材料代码不读取 Buda Adapter ID、工具名或 Agent 数量限制。
10. 非 Buda MCP Adapter 可以通过相同阶段合同执行。

### 校验和原子性测试

11. 完整 MCP 结果一次提交全部材料和引用。
12. 缺失必要分区、非法实体引用、超限内容或越权字段时零写入。
13. 提交前来源切换或上下文变化时零写入。
14. 保存中任一步骤失败时事务完整回滚。
15. 空字段不覆盖已有材料，规范化逻辑不创造小说语义。
16. 不确定 mutation 进入现有隔离流程且不会创建第二个 Agent Session。

### 页面和章节链测试

17. MCP 激活且无模型 ID 时，“补齐材料”和“生成正文”均可启动。
18. 模型激活且无模型 ID 时继续显示原有模型提示。
19. 手动补齐成功后刷新所有材料模块和评分。
20. 自动补齐成功后重建上下文，再开始新的正文 Session。
21. 补齐失败时不继续生成正文，也不自动切换来源。

### 回归与真实验收

22. GenerationSource、MCP Adapter、Server、Web 和完整项目门禁通过。
23. 现有模型 API 补齐、正文、复检、修订和 Story State 测试保持通过。
24. 使用两个独立测试账号分别从页面执行“补齐材料 → 生成第一章”。
25. 每个项目核对唯一来源、材料评分、严格 preflight、正文、独立 Session 回执和 quarantine 状态。
26. 真实验收及提交内容不包含账号凭据、Key、完整 Agent/Session ID、远端完整错误体或生成正文。

## 非目标

- 把 Buda 的页面、账号或工具定义写入通用材料编排。
- 让远端 Agent 的长期记忆取代 MangaForge 权威上下文。
- 在同一个远端 Agent Session 内继续生成正文、复检或修订。
- MCP 失败后自动切换模型 API。
- 本期统一或重写模型 API 的既有补齐实现。
- 改变 Express/Bun 的 HTTP 提交语义。
- 自动清理既有 quarantine。
- 实施 Key 静态加密。
- 扩展到章节生产链之外的素材、漫画或知识库生产流程。

## 验收标准

- MCP 项目无需选择 API 模型即可从页面补齐所有缺失的章节前置材料。
- 一次补齐操作只创建一个远端 Agent Session，后续正文使用另一个 Session。
- MCP 补齐结果经过整体校验和原子提交，失败时没有半成品。
- MCP 失败不回退 API，也不由模板生成小说语义内容。
- 手动补齐和正文启动时自动补齐共用同一个服务。
- 页面补齐后刷新材料和评分，并能继续通过严格 preflight 生成正文。
- 通用编排和合同不依赖 Buda，其他 MCP Adapter 可以实现相同能力。
- 模型 API 的补齐、正文、复检、修订、Story State 和页面行为没有回归。
- 自动化门禁以及两个账号的页面真实验收全部通过。
