# 编辑器修订项目级超时配置设计

日期：2026-07-30
状态：已确认，待实施
范围：单章编辑器修订链路的模型调用超时配置

## 1. 背景与现场证据

项目 `3` 的第一章修订任务 `#755` 使用健康的 v4 正文启动，源正文约 5692 字，审查记录为 `#12312`，模型为 `#36`，策略为 `structural_rewrite`。任务从 `2026-07-30T00:18:29.558Z` 运行到 `2026-07-30T00:21:29.765Z`，在 `generate_candidate` 阶段以 `REVISION_LLM_TIMEOUT` 失败，正文未写入。

失败持续时间与 `revision-worker.ts` 中硬编码的 `180_000` 毫秒完全一致。模型 provider 本身支持 600 秒，但 worker 同时用 180 秒控制本地中止定时器和 provider 的 `timeoutMs`，因此 worker 是当前瓶颈。此次失败不是 JSON 解析问题，也不是章节回滚后的正文损坏。

## 2. 目标

1. 把单章编辑器修订的单次模型调用超时改为项目级配置。
2. 默认值为 600 秒，可配置范围为 60 至 600 秒。
3. 候选正文生成、修订后质检、Story State 准备和应用统一使用该配置。
4. 配置只影响当前项目以及之后启动或重新执行的修订任务。
5. 保留现有重试次数、取消、租约续期、失败检查点和单章作用域。
6. 在任务检查点中记录实际采用的超时，便于诊断和恢复。

## 3. 方案选择

评估过三种方案：

- 全局常量：改动最少，但所有项目只能使用同一超时，无法满足项目级调整。
- 模型级配置：适合 provider 通用运行参数，但同一模型在正文生成与短响应任务中的等待需求不同，作用域过宽。
- 项目级修订配置：将设置限定在当前小说项目的编辑器修订链路，默认 600 秒并允许项目内调整。

采用第三种方案。它与故障链路边界一致，也不会改变其他模型功能的超时。

## 4. 配置模型与接口

配置保存在项目现有的 `reference_config` JSON 中：

```json
{
  "editor_revision": {
    "timeout_seconds": 600
  }
}
```

新增一个集中式纯函数负责归一化有效值：

- 缺失、非数字或非有限值回退到 600 秒；
- 有限数值取整数后限制在 60 至 600 秒；
- worker 和项目配置接口共用同一归一化逻辑，避免前后端或执行路径出现不同默认值。

新增专用项目接口：

- `GET /api/novel/projects/:id/editor-revision-config`
- `PUT /api/novel/projects/:id/editor-revision-config`

GET 返回归一化后的有效配置。PUT 要求请求值是有限数字，有限的越界值按 60 至 600 秒限制，非数字或非有限输入返回 400。PUT 只合并 `reference_config.editor_revision`，必须保留 `reference_config` 中的参考作品、写作圣经、Story State、质量门和其他字段。不存在的项目返回 404；持久化失败返回 500。数据库中已有的缺失或非法旧值仍按默认 600 秒读取。

旧项目不做数据库迁移。未保存该字段时自然使用 600 秒默认值。

## 5. Worker 数据流

worker 认领任务并加载项目后，按以下顺序确定超时：

1. 若当前任务检查点已有合法的运行时超时快照，继续使用该值；
2. 否则从项目配置解析有效值，并在第一次模型调用前写入检查点；
3. 将秒转换为毫秒，传给本地中止定时器和 provider 的 `timeoutMs`。

检查点新增可选运行时字段：

```json
{
  "runtime_config": {
    "llm_timeout_ms": 600000
  }
}
```

同一个任务在 worker 重启或租约恢复后继续使用原快照。修改项目设置不会改变已经开始的任务；重新执行产生的新任务会读取最新项目设置。

统一超时覆盖以下模型阶段：

1. `generate_candidate` 的候选正文生成；
2. `post_quality` 的修订后质检；
3. `sync_current_story_state` 的 Story State 准备；
4. `sync_current_story_state` 的 Story State 应用。

`maxRetries` 继续保持为 `1`，不增加模型调用次数。租约心跳和用户取消信号继续独立工作，600 秒等待期间仍能取消任务。

## 6. 界面设计

小说工作台右上角“更多”菜单增加“项目设置”入口。入口打开一个轻量项目设置弹窗，首个设置区为“质检与修订”。

该设置区包含一个数字输入框：

- 标签：`单次模型调用超时`
- 单位：秒
- 最小值：60
- 最大值：600
- 默认值：600
- 只允许整数

辅助说明明确：该值是每个模型阶段的最长等待时间；一次修订可能包含多个阶段，因此整次任务总耗时可能超过该值。

弹窗打开时通过专用 GET 接口读取有效值。保存时通过专用 PUT 接口更新；保存成功后关闭并提示成功，保存失败时保留用户输入并展示服务端错误，不误报成功。此设置不放入“参考作品配置”弹窗，避免把运行参数与参考内容混在一起。

## 7. 错误与诊断语义

超时继续使用稳定错误码 `REVISION_LLM_TIMEOUT`。错误信息包含实际等待值，例如：

```text
editor revision model call timed out after 600 seconds
```

任务中心可以继续按原错误码识别失败；检查点中的 `runtime_config.llm_timeout_ms` 用于确认实际配置。候选生成超时时正文保持不变；后置质检或 Story State 超时时保留已经提交的候选正文，并把实际失败阶段、完成时间和错误信息按现有检查点机制持久化。本次不改变阶段顺序或回滚语义。

## 8. 测试

### 8.1 配置归一化

覆盖缺失值、非法值、非有限值、整数值、小于 60、大于 600 和小数值，确认默认值与边界一致。

### 8.2 项目接口

覆盖 GET 默认值、PUT 保存、边界归一化、错误请求、项目不存在，以及更新后其他 `reference_config` 字段保持不变。

### 8.3 Worker

覆盖以下行为：

1. 默认配置在 600 秒触发本地中止并返回 `REVISION_LLM_TIMEOUT`；
2. 自定义项目配置同时传给本地定时器和 provider；
3. 候选生成、后置质检、Story State 准备和应用使用相同超时；
4. 检查点在首次调用前保存运行时快照；
5. 同一任务恢复时复用检查点快照，新任务读取最新项目配置；
6. provider 重试上限仍为一次重试；
7. 超时期间取消和租约续期行为不回归；
8. 超时失败时章节正文未写入，失败检查点完整。

### 8.4 Web

覆盖“更多”菜单入口、弹窗加载默认值、60 至 600 秒校验、保存请求、保存失败保留输入，以及成功后关闭与提示。

## 9. 非目标

- 不修改其他小说生成、审查或诊断任务的超时；
- 不增加重试次数或自动发起新的模型调用；
- 不扩展到批量章节或全部章节；
- 不改变候选准入、JSON 恢复或正文持久化规则；
- 不修改 `workspace/novel.sqlite`、章节正文或历史版本；
- 不覆盖当前工作区中尚未提交的 JSON 双引号修复。
